# 教学数据与图示

全部数值案例为教学构造数据。金额单位为整数分，时间单位为毫秒；正文用秒展示时明确标注。课堂时间戳以起点为零。

## 主案例

`events`按到达次序排列，共12条投递、9条成功记录、8个唯一成功事件。E03被投递两次；FAILED、PENDING、CANCELLED各一条。按eventId去重后，用户A/B/C金额为6000/14000/12000分，总计32000分。partition内Offset递增；eventId、orderId和Offset具有不同用途。

## 窗口专项

A—H复用主案例八个成功事件的时间和金额，用字母便于跟踪。L（8000ms，2500分）和X（6000ms，1000分）是新增成功事件，与主案例的失败记录无关。按照达顺序处理每条事件后，课堂发出 `maxTimestamp−2000−1` 水位线。实际周期生成器的发出频率由配置决定。

窗口大小10000ms，默认专项允许迟到5000ms。窗口首次触发时间为end−1，清理时间为end−1+allowedLateness。输入结束采用有界源终止水位线，不能把墙钟推进替代事件时间进度。L被接纳并使首窗口输出16500分；X进入侧输出。

## 匹配与执行专项

O1—O4为独立的订单创建/支付数据；匹配范围包含两端，`0≤payTime−createTime≤5000`。超时计时器设为createTime+5001。专项插入W=8001与W=15001；有效且在计时器前被接纳的支付进入PAID，未支付到期进入EXPIRED。结束后到达的支付保留到补核，不自动撤回超时。O1/O3匹配，金额5000分。TTL专项另外选择处理时间、创建/写入刷新、过期不返回；TTL不承担业务超时输出。runtime中的吞吐能力为给定条件，均匀分区和热点模型分别计算。

## 故障专项

使用八个唯一成功事件的独立双分区源：A的100—103依次为E01/E03/E05/E07，B的200—203依次为E02/E04/E06/E08。这里的Offset独立于主案例原始投递日志。

完成检查点包含前四事件、金额14000分、A.next=102、B.next=202。故障前再处理E05/E06得到21000分；恢复后重放E05—E08得到32000分。外部盲目追加则产生10行、39000分。

## 图示复现

PlantUML源稿覆盖六类图：类图、活动图、组件图、部署图、状态机图、时序图。第1至4讲的158幅机制场景由 `course/story/lesson-01..04.json` 与 `scripts/course_story.py` 生成；第5讲由 `scripts/render-lesson-05.py` 生成。通用图示见 `scripts/render-diagrams.py`，Mermaid DAG源码见 `course/diagrams/*.mmd`。SVG与场景参数均可编辑，放映使用本地资产。字体优先PingFang SC，教学页继承easy-jyy。PlantUML工具版本1.2025.0，下载文件SHA-256固定在脚本中。
